## Day one

Coming in for another shift at the office factory and opening the laptop, the first thing I see is a notification from L2 support saying that several overnight runs in our ETL app have failed. Naturally, the first thing we go and do is open the logs. But before that, a bit about the stack:

* Java
* Agroal (connection pool, and it matters that this sits at the Java app instance level)
* Databases: Databricks, MSSQL, Oracle

So, in the logs, while finding the record of a new app instance being created, I also find the exact moment the instance dies. No OOM and no exceptions in the logs. Going in through container management, we find error 137 (the container ran out of memory and decided to kill the app).

You would think, how is that even possible? If the app had run out of memory, we would have had a nice OOM message from Java. Naturally we checked the settings (is there a case where container memory is smaller than JVM memory), made sure that was not so and that the container adjusts based on JVM memory numbers.

We went to look at the JVM memory metrics. We see that there is indeed a spike right before the instance dies, but it still does not reach the ceiling (another 30 percent left in reserve). Smart readers will say that is logical: the metrics push could have missed its slot, and the next time window simply never got sent. But even taking a linear function, there was still room. And that again does not answer the question of why Java did not send an OOM (for non Java people, a reminder: the JVM reserves memory for the OOM error and its log right at the start, so it will always manage to write the error before going down).

The only steady growth we see is G1 Old Gen. I will not go into a detailed walkthrough of how GC generations work. In Java terms, for our investigation, this only tells us a few things:

* large objects go straight into Old Gen;
* many objects are not collected and get promoted into Old Gen (potentially the first hint, something may be holding a strong reference in the app);
* every GC round over the last 2 minutes did not actually reduce the amount of memory, it just moved objects from Young Gen into Old Gen.

A separate note about the right hand side of the chart: the flat part is not memory stabilising, it is the moment the pod is already dead and the metric stopped arriving, while Grafana keeps pulling the last value forward. Read without attention, it says exactly the opposite.

Having analysed the rest of the memory related metrics, we come to the conclusion that there is no more useful information. At that moment it becomes clear that there is most likely some resource leak in the app, and that we really ought to take a heap dump and look at it, maybe it gives us something. But here we had two problems:

* a heap dump is generated, with the right settings, in the case of an OOM (not our case);
* a heap dump is generated by a command, which means it is the current state of the system, and if this was an exceptional situation, the dump goes nowhere useful.

Since the first option is not ours, only the second one is left. Naturally, as it goes in corporations, everything needs permissions: we have no direct access to the containers, so we have to write to the operations team to get us a dump. And we get it!

IntelliJ takes a nastily long time to open it, you have to wait 15 minutes for it to load. Eventually we get it. And here you have to stop and think about what exactly we are looking for:

* we are looking for whatever weighs a lot of memory;
* we are looking for something suspicious in the threads;
* we are looking for something suspicious in the references.

The first one falls away immediately, because the usual sorting inside the dump shows us the usual byte arrays and concurrent hash maps, everything within normal range, none of our own objects anywhere in sight.

But the threads give us the first genuinely surprising behaviour. In them we notice the first oddity, namely threads hanging in waiting state and sitting in the connection pool. There were around 10 of them. And why is that odd? The Databricks API does not allow long lived connections, so by design we do not put them in the pool and do not use the connection pool for them at all, yet for some reason we see them sitting right there (spoiler: the answer will be found).

In everything else the threads give us no hints. That leaves the references. They can potentially hold leaks. How? For example, if you have references to 100+ connections, each one holding a session, that is an excellent example of a leak. Or other objects that should be closed and collected by GC but for some reason are not. The analysis showed that sessions at the database level are closed and the numbers are within normal range. As for files, we do not see any specific sessions, so at this point we conclude that there is no leak.

The Databricks bug does not explain the memory problem. The first working day is over and we still have no leads.

## Day two

The same notification from L2 support, a pod goes down again, first one, then a second one, then again the one that had just been created. The charts give the same numbers, the container kills it again. In general, nothing changes.

Scrolling through the logs at some point, I come across a run name and realise that it matches the name of a run from the day before. Opening them, we notice that this is a run that works with 70 files. Which, within our system, is a perfectly reasonable number, since our system happily copes with runs of 150+ files as well. But something is clearly off, why does it fail twice?

Opening the app dashboard, which has a histogram of runs, we notice that one of the users started this run 3 times in a row within 0.1 seconds. Which does raise the question of why you would start an identical run. That explains the spike, but it still does not explain why the instance dies.

We start digging into the code and find an absolutely silly mistake. Our reading is usually done lazily, but specifically in the case of this GroupReader (the class responsible for reading files that come in groups) it opens connections to them straight away. In other words, the system normally reads from N files at a time, where N is set by the user. But in this case there was no N, and connections were created to all 70 files at once, while there was no simultaneous reading from those 70 files. In other words, 70 threads were created.

But that still did not quite explain the cause. Fine, a lot of threads were created, say 300+, how does that matter? You would think they are just hanging there doing nothing.

A caveat is needed here, because the metrics show the opposite: the runnable line jumps while waiting and timed_waiting stay flat. A thread blocked on a socket read is reported by Java as RUNNABLE, because the blocking itself happens in a native method. So these are not sleeping threads, these are live reads, each with its own stack and its own buffers.

And here an unexpected guest shows up. In our case reads and writes go through a network drive, we use the SMB protocol and a library maintained by a one man show. A long time ago, a couple of years back, we found a bug where this SMB library did not close sessions right away but did it 30 minutes later: the guy had a missing `if` condition. We patched it, made a PR, and thought that was that. But after that we put two and two together and realised that in fact the session was not being closed at the library level, so our app had the same 30 minute delay.

Only then did we work out why we had not noticed a thread spike in Grafana: because the system survived the first jump, that is, the first start. The last 2 starts it did not (the same user started them 3 times in a row).

Starting it twice, we saw the thread count grow from N to N plus the number of files GroupReader was reading. Since the session hangs for 30 minutes, that new thread count will hang for 30 minutes. Someone else can kick off something on top of that, and so on.

## The culprit

A thread is native memory. Every Java thread gets its own stack (1 MB by default, `-Xss`) plus the native structures of the thread itself. Native memory is not in the heap, which is why heap metrics and the heap dump are clean. Native memory is not in the off heap line on the chart either.

Threads are fully counted in the process RSS, and therefore in the container memory limit. If the container has, say, 1 GB and `MaxRAMPercentage=75`, then everything native is left with roughly 250 MB, which the threads ate entirely.

What happens next has nothing to do with the container itself. The memory limit is a cgroup, and when the memory of the processes inside it hits the ceiling and nothing can be reclaimed, the kernel OOM killer picks a victim and sends it `SIGKILL`. We have a single JVM in that cgroup, so the choice is obvious.

And there was no OOM from Java because the JVM never hit its heap ceiling at all. It was killed from the outside, not from the inside.

1. Fixed a bug in GroupReader that had been there for almost 2 years!
2. Although my colleague primarily blames the user, I think this is bad work by my team, myself included. Namely: the silly GroupReader bug and, second, poor dependency management. We need to keep a closer eye on the issues we open and on the ones that are already open.
3. Regular heap dumps can highlight details. In our case we fixed a Databricks bug on our side: a property had been forgotten, and any sessions were always returned back to the pool, even though with Databricks we do not want that.
4. We also decided to stop users from launching something with identical properties until a reasonable window has passed.
5. We decided to add metrics on network operations, to avoid possible resource leaks.
6. Container metrics are needed just as much as JVM metrics. All this time we were looking at the heap, while the process was being killed for native memory, which simply is not in heap metrics. The process RSS and the container memory limit would have shown the problem straight away.
